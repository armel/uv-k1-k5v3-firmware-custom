# F4HWN v6.2 merge: open considerations

Merge branch: `dev/f4hwn_6.2`, merging upstream tag `v6.2.0` (armel) into our CW fork.

The merge builds and runs the CHIRP tests, but it hasn't run on a radio yet. Each section says what the branch does now, why, and what still needs a decision. Nothing here is final.

## 1. Weak-signal RX filter

### Background

`BK4819_SetFilterBandwidth(bw, weak_no_different)` sets REG_43. The second argument chooses whether the RF filter keeps its width when the signal is weak (`true`) or steps one notch narrower (`false`). Taken from `bk4819.c`:

| Preset | Strong-signal RF BW code | Weak, `true` | Weak, `false` |
|---|---|---|---|
| WIDE (25k) `0x3628` / `0x3428` | 3 | 3 | 2 |
| NARROW (12.5k) `0x3648` / `0x3448` | 3 | 3 | 2 |
| NARROWER (6.25k) `0x1348` / `0x1148` | 1 | 1 | 0 |

CW and USB always resolve to NARROWER (`RADIO_ResolveFilter`). AM uses its own pair.

### History

- **Upstream, every version:** non-AM gets `false` and AM gets `true`. Code under `#ifdef ENABLE_AM_FIX` passed `true`, but the build never defined `ENABLE_AM_FIX`, so that branch never ran. v6.2 deleted it (`66fb8b1e`) without changing behavior.
- **Our fork up to v1.3.x:** same as upstream, plus a separate "narrowest" (2k) CW/USB filter set with `false`.
- **Our fork in v1.4** (`f7b8801f`, the schema 2 filter rework): we dropped the 2k filter on purpose. On the BK4829 in baseband (CW/USB), no filter setting below 6k has made any audible difference to the AF output in our testing. CW and USB now always use the 6.25k (NARROWER) preset, and the filter call became one `BK4819_SetFilterBandwidth(Bandwidth, true)` for every mode, in RX and TX setup.

### What the flag means for each mode

- **CW and USB:** the flag only picks the weak-signal code inside the 6.25k preset, 1 (2.0k) with `true` or 0 (1.7k) with `false`. Both are below 6k, so by our measurements the choice is inaudible either way. That's a claim we'd welcome being proven wrong on.
- **AM:** `true` everywhere, upstream and ours.
- **FM:** the one mode where this is a real choice. 25k and 12.5k narrow from code 3 to 2 on weak signals with `false` and hold at 3 with `true`. Upstream has always used `false`; v1.4 shipped `true` as part of the single call above.

### Upstream v6.2: anything new for baseband audio?

No.

- **Resident firmware:** upstream's only changes to the BK4819/BK4829 drivers are the DCS tail-tone fix (`c7a6d11d`, REG_52 bit 15) and the AirCopy FSK framing. RX setup only lost the dead AM_FIX code.
- **Overlay apps CW Keyer and CW Decode** (`apps/cwkeyer`, `apps/cwdecode`, overlay builds only): they use the same USB product-detector path we do. AF mode 5 (`BASEBAND2`), REG_31 AM bit cleared, REG_42 `0x6B5A`, REG_2A `0x7400`, REG_2F `0x9890`, REG_54/55 `0x9009`/`0x31A9`, REG_3D `0`, AFC disabled (REG_73 bit 4), AGC on. They tune the receiver 700 Hz below the carrier, as our cross-mode pitch does.
  - The only register difference from our CW profile: REG_2B `0x0000` (theirs) vs `0x0500` (ours, from the AM "sharp" profile).
  - They never call `BK4819_SetFilterBandwidth`, so REG_43 is whatever the resident firmware left.
- **CW Decode** decodes from the RSSI envelope rather than from audio. Possibly interesting as a technique, but not a filter.
- **CW Keyer** shapes TX keying edges by ramping the PA bias byte in REG_36 over 4 ms, with modulation muted and the sidetone routed through the alarm-audio path. That's TX-side, but worth comparing with our keying envelope.

### Merge branch now

`RADIO_FilterHoldsOnWeakSignal()` in `radio.c` returns:

- AM: `true`
- FM: `false` (upstream)
- CW and USB: `true` (v1.4, inside `#ifdef ENABLE_CW_MODULATOR`; inaudible either way, per the above)

### Decided

- **FM follows upstream: `false`** (narrows on weak signals). Armel has far more FM tuning experience. This is a deliberate behavior change from v1.4, and the merge branch already does it.
- **CW/USB stay on `true`** for the merge, so their register values are exactly v1.4's.
- **REG_2B stays at `0x0500`.** It does nothing in baseband (it was an experiment that didn't pan out), but it's harmless, so we're not touching it in the merge.

### Future experiment (not part of the merge)

Try CW/USB with `false`, so the sub-6k setting is used only as the weak-signal step-down: the 6.25k preset at normal levels, code 0 (1.7k) when the signal is weak. A sub-6k filter selected outright made no audible difference, but as the weak-signal setting it might behave differently. If it helps, it's a one-line change in `RADIO_FilterHoldsOnWeakSignal()`.

## 2. Calibration sector

Calibration lives at flash `0x010000` (logical `0xB000`–`0xB200`). Under multiboot it is **shared** by every slot and bank (`PY25Q16_BANK_SHARED_FROM`).

### 2a. Frequency calibration menu (F_CAL) write address

- **Ours** (`078c8415`, fixes issue #10): `app/menu.c` reads and writes the crystal offset at flash `0x010188` directly, which is where `SETTINGS_LoadCalibration` reads it from.
- **Upstream v6.2, still:** it uses `EEPROM_ReadBuffer/WriteBuffer(0x1F88, …)`. That is the old 8 KB EEPROM address. Through the current compat map, logical `0x1F88` lands in the channel records (flash `0x1F88`, bytes 8–15 of channel record 504, shown as channel 505). So upstream's F_CAL menu corrupts a channel and never reaches calibration.
- **Merge branch:** keeps ours.

**Decided:** keep ours. Calibration is a radio-wide value regardless of multiboot. Still worth sending upstream as a PR: once it lands, it stops coming back as a conflict on every merge.

**Not the same thing: the CW Keyer overlay's `XTAL` correction.** Upstream's overlay keeps its own crystal correction (`calCentiPpm`, in hundredths of a ppm).
- **Where it lives:** in the app's config slot in the overlay area, not in the calibration sector.
- **How it works:** the app scales the frequency it programs into the synthesizer (REG_38/39), on both RX and TX. F_CAL instead trims the crystal through REG_3B, so the two stack. A radio with F_CAL already set would be corrected twice inside the app.
- **Default:** +2.77 ppm, measured on one radio ("+400 Hz at 144.225 MHz, +1.20 kHz at 433.225 MHz"). Every radio starts with that radio's error.
- **Relevance:** none for us while the CW preset leaves overlay apps off. Worth knowing if we ever turn them on, and maybe worth mentioning to upstream.

### 2b. Settings saves write into the calibration sector

Upstream's `SETTINGS_WriteCurrentVol()` (`ENABLE_FEAT_F4HWN_VOL`, which the CW preset enables) writes VOLUME_GAIN into `0x010188`. It is called on every `SETTINGS_SaveSettings()`, and has been since before this merge.

How often that actually touches the flash:

- **Usually never.** `PY25Q16_WriteBuffer` compares against the sector first and skips the write when the bytes are unchanged. So in practice it writes only when VOLUME_GAIN has changed since the last save.
- **SetVol** (a regular, visible F4HWN menu item, not hidden like FrCali) changes it on purpose.
- **The MUTE key action** changes it as a side effect: `ACTION_Mute` sets VOLUME_GAIN to 0 and restores it from `VOLUME_GAIN_BACKUP` when unmuting.
- **When the value drops** (muting, or lowering SetVol), only bits are cleared, so the write programs in place. **When it rises** (unmuting, or raising SetVol), bits must be set, so the next save **erases and rewrites the whole calibration sector**. A power cut during that erase loses the radio's factory calibration. A routine mute/unmute followed by any settings change is enough to trigger it.
- **Probable side bug, untested:** mute, then anything that saves settings, then reboot. The radio likely comes up at volume 0, because VOLUME_GAIN loads as 0 and `VOLUME_GAIN_BACKUP` is copied from it at boot.
- **F_CAL:** the menu write has the same erase exposure, but only when someone uses the hidden calibration menu.
- **Multiboot:** the volume gain is one value for every firmware slot, while everything else in settings is per bank.

**To decide:**

- Do we accept this? It is upstream behavior and affects every F4HWN radio.
- Or do we move VOLUME_GAIN to a per-bank spot in the CW block reserve (`0xA210`–`0xA23F`)? That stops routine saves from erasing the calibration sector in our build, but diverges from upstream and needs a migration.
- Either way, worth raising upstream.

## 3. Debug prints and the minimal printf

Upstream switched `external/printf` to `PRINTF_USE_MINIMAL` (`a8dd3259`), which supports only `%d %u %o %s %c %%`. It also added `cmake/check_printf_formats.py`, which fails the build on any other format string in `App/`. The checker only skips code inside `#ifdef DEBUG` / `#if defined(DEBUG)`.

Our CW debug code is guarded by `#if ENABLE_CW_HARDWARE_DEBUG`, `CW_MACRO_DEBUG`, `CW_ENCODER_DEBUG` and `USB_PADDLE_DEBUG`, all defined as 0. The checker doesn't evaluate those, so it flagged 9 hex formats (`%08X`, `%02x`) in `cwhardware.c` and `cwmacro.c`.

### Merge branch now

Those formats became `%u`. The prints still compile and print decimal. It is cosmetic, but register dumps and bitmasks are harder to read.

### Options

1. **Leave `%u`.** Zero cost.
2. **Add a small hex helper** (one nibble-to-char loop) used only inside the debug blocks. Readable output, no cost when debug is off.
3. **Teach the checker about our guards**, for example skip `#if *_DEBUG` blocks whose macro is 0. Hex formats would then compile, but print wrong at runtime under the minimal printf unless option 4 is also done.
4. **Use the full printf when a CW debug flag is on.** Costs flash, which matters at 4.3 KiB free.

Related: several of these debug paths print over the UART on PA10, which the keyer also uses (see the comment in `cwhardware.c`). Worth deciding whether these debug blocks should survive at all, or move to a single `ENABLE_CW_DEBUG` that the checker and CMake both understand.

## 4. Multiboot config space

### Upstream's layout

From `driver/mb_flash.h`:

| Range | Use |
|---|---|
| `0x000000`–`0x00FFFF` | Config bank 0, **per bank** (everything below `0x010000` is shifted by the active bank's base) |
| `0x010000` | Calibration, shared |
| `0x011000` | Boot logo, shared |
| `0x018000` | RX/TX log, shared |
| `0x020000`–`0x0BFFFF` | Firmware slots 0–4 (slot 0 is the self-backup) |
| `0x0C0000`–`0x0FFFFF` | Config banks 1–4, 64 KiB each |
| `0x100000`, `0x101000` | Multiboot state markers A and B |
| `0x102000` and up | Overlay apps |

### Our CW storage in it

| Data | Flash | Logical (CHIRP) | Banked? |
|---|---|---|---|
| CW block (`CWX` header, schema, CW settings, 48 B reserve) | `0xA200`–`0xA23F` | same | yes |
| CW macros (`CWM` header, 4 × 48 B, spare) | `0xB000`–`0xB0FF` (own sector) | `0xD000`–`0xD0FF` | yes |

### Checked, no conflict

- **Bank-relative.** Both areas sit below `0x010000`, so every bank gets its own copy.
- **Erased with the bank.** Erasing a bank (`MB_BankErase`) clears the full 64 KiB.
- **Banked I/O paths.** CHIRP and the UART go through the compat map into `PY25Q16_ReadBuffer`, which applies the bank base. CHIRP always sees the active bank.
- **Host tools and overlay apps.**
  - Host raw flash access (`0x0738`–`0x073E`, UV Studio) covers the whole chip by physical address and only protects calibration.
  - Overlay apps keep their config in their own slots at `0x102000+`, not in the bank.
- **Settings ranges.**
  - Upstream's settings end at `0xA178`; `0xA178`–`0xA1FF` is left for upstream growth.
  - Our `0xA000` compat mapping runs through `0xA240` on purpose (see the comment in `eeprom_compat.c`).
- **Live bank switch** (SetCfg with HOT_CFG):
  - `MB_ApplyBankMapping` then calls `SETTINGS_InitEEPROM(true)`, which re-runs `SETTINGS_InitCwBlock` for the new bank.
  - Macros are read from flash on demand, so nothing stale is left in RAM.

### Open points

- **The CW preset must build with `ENABLE_FEAT_F4HWN_MULTIBOOT`.** Without it, our firmware started from a slot never sets a bank base: it runs on bank 0, which belongs to whatever firmware owns it, and migrates that data. The merge turns on MULTIBOOT, HOT_CFG and MULTIBOOT_OVERLAY in the CW preset. Flash is at 113.7 of 118 KiB.
- **UV Studio's view of a bank.** Upstream's `mb_flash.h` says the "max physical config address" is `0xA170` (out of date, comment only). Does UV Studio's config backup, restore or copy work on whole 64 KiB banks, or on a fixed range? If it's a range, our `0xA200` block and `0xB000` macro sector would be left behind. Needs checking against UV Studio.
- **Upstream growth past `0xA200`.** Upstream has about 136 bytes of room before our CW block. Worth asking armel to treat `0xA200`–`0xA23F` and the `0xB000` sector as reserved, or at least to tell us before using them.
- **Shared values.** Calibration (and volume gain, see 2b) is one value for every slot. Everything else is per bank.
- **Upstream's own CW Keyer overlay app** (`apps/cwkeyer`, plus CW Decode). It only exists with `ENABLE_FEAT_F4HWN_OVERLAY_APPS`, which the CW preset leaves off. If we ever turn overlay apps on, two keyers would compete for the same inputs.

## 5. Bank migration

### No in-firmware migration

v2.0 does not migrate v1.x data. The v1.x layout is converted only by the CHIRP module, from an image saved before the upgrade (README, "Upgrading from v1.x to v2.0"). `SETTINGS_InitCwBlock` runs on every boot and every bank switch. When the bank has no valid `CWX` header, it:

1. Resets the five key action bytes at `0xA0A8` to unset (defaults), **unless** `0xA170` carries the `MIX` signature. Upstream v6.2 stores the same fixed IDs and writes `MIX` on every settings save. The beep bit is kept.
2. Writes the `CWX` header with schema 2.

Both steps are safe to repeat, so a power cut before the header write just reruns them. Nothing else is touched: channels, `0xA140`–`0xA147`, `0xA170`, the legacy macro bytes at `0x1C00` and the macro sector. With no `CWM` header there are no macros, and the first save writes the header.

### How a bank gets here

| Situation | What the bank holds | What happens |
|---|---|---|
| v1.4 radio, USB-flashed to this firmware | Our v1.4 data, in bank 0 | Keys reset to defaults; CW settings and macros start at defaults; channels kept (pre-v1.4 CW/USB keep their old filter bits). Documented path: Reset ALL, then upload the converted CHIRP image. |
| Multiboot radio, our firmware restored into slot N for the first time | Empty bank N (upstream does not copy bank 0 into new banks) | Fresh-radio path: header written, nothing else. |
| USB-flashing our firmware onto a radio that is running multiboot | Boot resolution notices the image changed, self-backs it up to slot 0, and uses bank 0 | Bank 0 may hold stock F4HWN data. See the next two rows. |
| SetCfg to a bank last used by stock F4HWN that **has saved settings** | `MIX` at `0xA170` | Everything kept; only the header is written. |
| SetCfg to a stock bank that **never saved settings** | No `MIX`, erased `0xA170` | Key bytes reset, which changes nothing since they are already erased. Header written. |
| armel v6.1 data | `MIX` | Treated as v6.2: keys kept. v6.1 numbered actions by build options, differently per edition, so binds may point at the wrong action. Upstream's own v6.1→v6.2 upgrade has the same problem. |

### Going the other way: stock firmware on a bank we used

- **Key actions:** our CW IDs (32–45) fail stock's range check (`< 25`), so stock runs its defaults for those keys. Upstream IDs we stored mean the same thing to stock.
- **CW data:** stock ignores the CW block and the macro sector. Stock's CHIRP never sees them, because its compat map ends at `0xA178`.
- **Unchecked:** what stock F4HWN does with channels whose modulation is CW (value 3), which it doesn't have.

### To decide

- **Whether SetCfg should convert a foreign bank at all.** Today, switching to another edition's bank writes our `CWX` header into it (and resets its key bytes if it has no `MIX`). Alternatives: do nothing until a CW setting is saved, or warn.
- **Seeding a new bank.** A slot's first boot starts with an empty bank. Is that what users expect, or should UV Studio (or we) copy channels from bank 0?
